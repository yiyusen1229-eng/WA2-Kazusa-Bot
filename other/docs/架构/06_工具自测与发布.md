## 版本与更新提示

- 客户端启动 1.2 秒后请求 `/api/update`，后端拉 `version.json` 比对
- 有新版本 → 标题栏出现「发现新版本 x · 点此一键更新」→ 点击直接更新（`updater.py`），
  流程：`POST /api/update/apply` 后台跑 → 前端轮询 `GET /api/update/status` 显示百分比 →
  成功后提示「已更新到 x · 关掉重开生效」；失败时才退回「点此打开下载页」
- **发布时必须同时改**：仓库根 `version.json` 的 `version`、`program/src/version.py` 的 `VERSION`
- 本地测试：设 `WA2_UPDATE_URL=http://127.0.0.1:8798/version.json` 指向假版本文件

## 一键更新怎么处理「用户漏了两版」

补丁是「对某个基线」的 diff，漏两版就打不上。所以客户端不再走补丁链，而是取**最新整份代码**：

| 安装形态 | 做法 | 说明 |
|---|---|---|
| 是 `git clone`（有 `.git` 且装了 git） | `git fetch --depth=1 origin master` + `git reset --hard FETCH_HEAD` | 分分钟到最新；**会丢弃本地未提交的代码改动**（用户数据不在版本控制里，不受影响） |
| zip 安装（没有 `.git`） | 下载 `codeload.github.com/<repo>/zip/refs/heads/master` | 只覆盖白名单：`program/src`、`program/tools`、`program/tests`、`other/docs` + 根目录几个文件 |
| 共同点 | 覆盖前备份到 `program/work_scratch/update_backup_<时间>/`；失败自动还原 | 白名单**不含** `program/build_env/`（角色/存档/缓存/venv）、`program/res/`（素材）、`program/logs/` |

自测：`tools/test_update.py`（26 项，含用本地裸仓模拟远端的 git 模式）。

## 发布流程（约定第 12、13 条）

1. `git tag v<日期>-old`（把当前状态锚住，方便回滚）
2. 把**上一版补丁**合进 `master` 并提交（让 clone 下来就是最新代码）
3. 写**这一轮的更新日志**（单独一份文件，不要追加到旧日志）
4. 生成补丁：`git diff --binary <上一版>..HEAD -- . ":(exclude)other/docs/patches" > other/docs/patches/<日期>_更新补丁.patch`
5. 用临时 worktree 验证补丁能 `--check` 并 `apply`，否则别推
6. 更新 README 的更新条目与「文档」表，`git push`（**旧补丁不删**）

   **README 标题格式（2026-11-06 用户指定）**：
   `## YYYY-MM-DD-HH:MM:SS更新（大致内容）`，例如
   `## 2026-11-06-11:13:45更新（修复画面闪烁、演出自动切换、分支数量）`。
   时间取该版那份更新日志的文件名时间；新的排最上面，旧的不改标题以外的东西。
   不要写成「近期更新（…）」——用户要的是「时间戳+更新+（大致内容）」。

## 坑

- 补丁**不能包含 `other/docs/patches/` 自己**（否则每次重生成都在自我膨胀）。
- 补丁基线要写清（日志里写 `A → B`），否则别人不知道先打哪个。
- 探针截图会缩成 391×66，若真要截图就重跑；但默认**不要截图**。
