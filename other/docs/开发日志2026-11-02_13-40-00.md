## 二、语音端到端（边界，不是"通不通"）

用户已经能听到语音，这轮修的是**出错之后的样子**：

1. **`start()` 的 `_starting` 永久短路**（真 bug）：依赖缺失 / 启动失败 / 加载权重失败这三条早退路径
   都没复位 `_starting`，之后所有请求都直接返回 False，再也拉不起来。改成 `try/finally` 复位。
2. **合成串行**：`synthesize()` 加 `_synth_lock`，两个请求不会同时打 GPT-SoVITS；
   排队时先查缓存。
3. **缓存 key 加参考音频版本**：原来 key 只有 text/lang/emo，换了参考音频还会播旧缓存；
   现在把两个参考目录的 mtime 算进 key。
4. **挂掉能自愈**：连不上/超时时把 `_ready` 置 False，下一次请求会重新拉起；HTTP 4xx/5xx 不置（服务还活着）。
5. **`available()` 接受导入的参考音频**：原来硬要求自带 `refs_touma/1005_0427_01.wav` 存在，
   用户导入自己的参考音频反而"依赖缺失"。
6. **前端失败有提示**：`fetchVoice` 失败时在工具栏提示一次「语音暂时不可用，先显示文字」，不再静默。

**验证**：单测覆盖 `pick_ref` 优先级、`ref_audio_path` 透传、缓存命中、`_starting` 复位、连不上置未就绪、HTTP 错误不置。
真机 GPT-SoVITS 这次没起（避免拉几十 GB 的进程），链路行为用桩验证。

## 九、补记（14:02）：为什么「查看文件」打开是空的

用户反馈：提示词 / 世界书 / 记忆书 / 参考音频点「查看文件」，打开的都是空文件夹。

**原因**：那四个按钮打开的是**导入目录** `char/<kind>/`，只有「导入文件」成功过才有东西；
而程序真正读的是别处（`persona_core.txt`、`worldbook.json`、存档里的 memory、`tts/refs_touma`）。
所以没导入时打开就是空的 —— 看起来像没接线，其实是「中转站」和「实际读取位置」不是同一个地方。

**改法**：

- `special_files.open_target(kind)`：导入过 → 打开 `char/<kind>/` 并用 `explorer /select,<file>`
  高亮那个文件；没导入 → 打开程序**实际在读**的默认位置：
  `persona_core.txt` / `worldbook.json` / `sessions/` / `tts/refs_touma`。两边都不存在才回落到空目录。
- 下拉面板底部加一行「当前：persona_core.txt（默认）」/「当前：xxx（已导入）」，
  导入成功后立刻刷新 —— 不用点开文件夹也知道现在用的是哪份。
- `/api/special/status` 补 `path` 和 `source`（imported / default）；
  `char_file()` 默认按类型扩展名过滤（否则 `char/voice/` 里同名 `.txt` 会被当成"导入的音频"）。

**验证**：单测覆盖 4 个默认位置 + 导入后指向 + `explorer /select` 参数；
真机 `/api/special/status` 返回 `persona_core.txt` / `worldbook.json` / `sessions` / `refs_touma`；
探针里面板显示「当前：sessions/（默认）」；真机点「查看文件」返回 `source=default`、
`file=persona_core.txt` 并直接选中该文件。

## 十、补记（14:18）：记忆书简化 —— 存档只做一次拷贝，运行时只认缓存

### 两套「记忆书」不是一回事（之前文档没写清）

| | 特别模式的记忆书 | 存读档的记忆书（自动） |
|---|---|---|
| 是什么 | **角色固定设定**：她"本来就知道"的事 | 这局对话被折叠后的摘要 |
| 存在哪 | `char/memory/<文件>` | 存档的 `memory` 字段 + 运行时 `cache/memory_runtime.json` |
| 谁写 | 用户在特别模式导入 | 模型在对话超阈值时总结 |
| 何时用 | **每轮都作为固定前缀注入** | 超阈值后替代被折叠的旧对话 |
| 代码 | `char_res.memory_text()` | `memory.py` + `main._memory_context` |

两者的注入措辞也不同：自动的是「你记得的事」、固定的是「你记得的旧事（角色设定的一部分）」，
不会混成一段。system 的拼装顺序也按 `未完成功能.md` 里那条设计排好了：
**人设 → 常驻记忆书 → 世界书 → 对话记忆书 → 原作片段**。

### 历史记录对不上

`设计_上下文裁剪与记忆书.md`（2026-11-01）写的是「只在读档时判断、存档时异步总结」；
后来实现（`memory.py` 顶部注释）改成了「**游玩中途也判断**、条目先放运行时缓存」，
设计文档没同步 —— 所以看起来像两套说法。**以现在的代码为准**。

### 按用户要求简化（原来"存档后台再总结一遍"）

| | 旧流程 | 新流程 |
|---|---|---|
| 读档 | 有 memory 就把 entries/covered 接到运行时 | `memory.seed_from_save()` **整份复制**到 `cache/memory_runtime.json`，之后整局只读缓存 |
| 游玩 | 超阈值 → 最近段 + 条目；每 6 轮重打包 | 不变（`repack_turns = 6`） |
| 存档 | 先写快照，再**后台跑一次总结**补写 | **只把缓存整份快照进 `memory` 字段，不调用模型** |

删掉的代码：`main._finalize_save_memory`、`main._pack_until`、`sessions.session_patch_memory`
（以及每轮自动存档都会触发的那个后台总结线程）。

- 好处：自动存档不再可能顺带烧一次总结调用；读档路径只剩一条。
- 代价：存档里的 `covered_upto` 最多落后"最近段"6 轮；读档后若还没到重打包点，
  会稍微多发一点原文（`min(aligned, covered)` 兜底，不会留记忆空洞）。

### 验证（新增 `tools/test_memory_flow.py`，真后端 + 假模型）

- 读档 → `cache/memory_runtime.json` 里的 entries / covered / slot 与存档一致；
- 聊天 → 372 条历史里只发 116 条最近段，并注入缓存条目；
- 存档 → `memory` 与缓存一致，且**总结调用数为 0**；
- 连发 6 轮 → 第 6 轮触发后台总结，`covered` 追到最近段起点；
- 读一个没有记忆书的短档 → 缓存清空；
- 特别模式的固定记忆与自动记忆在同一条 system 里并存、标题不同。

### 两个要说明的

1. 自测第一次跑时 `_mem_llm` 走的是 `config.json` 里的真实端点，误发了一次总结请求（约几百 token）。
   已加 `WA2_MEM_URL` 测试缝，之后自测都指向本地假模型。
2. 本机现有存档（最多 140 条）都**没超过阈值**（当前 ctx=19200 → 触发 11520），
   `cache/memory_runtime.json` 也不存在 —— 不是没实现，是还没轮到它上场。
   想立刻看到效果，把特别模式的「上下文大小」调小，或继续聊到超阈值即可。
