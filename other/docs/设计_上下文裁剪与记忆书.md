# 设计：上下文裁剪与「记忆书」机制

> **2026-11-02 实施现状（和下面最初设计不一样的地方，以代码为准）**：
> - 阈值**游玩中途也会判断**，不只读档时（`memory.py` 顶部注释 + `main._memory_context`）；
> - **存档时不再异步总结**，运行时缓存就是唯一记忆书，存档只做一次快照；
> - 读档把存档里的记忆书整份复制进 `cache/memory_runtime.json`，之后整局只读缓存；
> - 每 `repack_turns = 6` 轮把新折叠的一段压进缓存。
> 下面的第六、七、十二节写的是最初方案（存档时生成、只在读档判断），保留作历史参考。
> 另：特别模式导入的「记忆书」是**常驻记忆书**（角色固定设定），和这里的对话记忆书是两回事，
> 见 `未完成功能.md` 的「两种记忆书的区别」。

> 目的：让存档可以无限增长，而送给模型的上下文永远可控。
> **前端零改动**——回想界面照旧显示全部原文，玩家感知不到任何变化。

---

## 一、要解决的问题

聊天越久，`messages` 越长。载入存档时全部塞回模型，会：

1. 撞上下文上限（直接报错）
2. 即使没撞，token 成本也随长度线性上升，回复还会变慢变差

**但存档文件不能丢内容**——回想界面要能翻到每一条原文。

所以：**存档保持完整，只裁剪「发送给模型的那一份」。**

---

## 二、核心设计

```
存档文件（不缩水）
├── messages[]        完整对话原文 ← 回想界面用这个
├── memory{...}       记忆书（新增字段）← 模型用这个
└── 其他原有字段

载入时组装上下文：
    [人设] + [世界书] + [记忆条目] + [最近 N 轮原文] + [本轮用户输入]
```

未超过阈值时，**保持现状**：全部 `messages` 直接发（此时 `memory` 为空或不存在）。

---

## 三、数据结构

存档文件新增一个可选字段，**旧存档没有它也能正常读**：

```json
{
  "slot": 3,
  "messages": [ ... 完整原文 ... ],
  "memory": {
    "enabled": true,
    "generated_at": "2026-11-01 18:00:00",
    "covered_upto": 120,          // 已经总结到第几条消息（索引）
    "entries": [
      { "text": "玩家说过不喜欢下雨", "from": [12, 18], "kind": "preference" },
      { "text": "两人约好周末去海边", "from": [40, 44], "kind": "event" },
      { "text": "当前进展：刚放学问完要不要一起走", "from": [114, 120], "kind": "progress" }
    ]
  }
}
```

要点：

- `entries[].from` 记录来源消息区间，**只用于调试回溯，不显示在前端**
- `kind` 分三类：`preference`（偏好）/ `event`（事件）/ `progress`（当前进展）
- `covered_upto` 是**增量总结的游标**，关键设计（见第六节）

---

## 四、参数与默认值

| 参数 | 默认 | 说明 |
|---|---|---|
| 触发阈值 | 模型上下文的 **60%** | 留 40% 给 人设 + 世界书 + 条目 + 回复 |
| 最近原文长度 | **8000 token**（可配） | 约 20~40 轮日常对话 |
| 每次生成条目数 | 5~10 条 | 少了丢信息，多了变噪音 |
| 条目全带界限 | 条目总量 < **2000 token** 就全带 | 超过再考虑检索 |
| 起点对齐 | 必须从**用户消息**开始 | 避免从半句切入 |

**最近段按 token 算，不要按轮数**——一轮可能一个字，也可能两千字。

---

## 五、token 估算

不引入 tokenizer，用近似公式：

```
中文：1 字符 ≈ 1 token
英文：4 字符 ≈ 1 token
合计后 × 1.05 作为安全余量
```

误差 10~15%，但阈值留了 40% 余量，可以接受。**不要为了精确去装 tiktoken。**

---

## 六、存档流程（关键：不能卡、不能坏）

```
1. 计算当前 messages 的估算 token
2. 未超阈值 → 照旧直接保存（memory 不写或写成 enabled:false）
3. 超过阈值 →
   a. 先把 messages 完整落盘，立即返回成功        ← 玩家立刻看到"已保存"
   b. memory 先写 {"enabled": true, "entries": [], "generated_at": null}
   c. 异步（后台线程）生成条目，写回同一文件
   d. 生成失败 → 保持空 entries，读档时自动降级为全量发送
```

**红线**：摘要生成失败**绝不能**导致存档写不进去，也**绝不能**导致读不了档。

### 增量总结，避免漂移

每次只总结**被新截掉的那一段**，追加到 `entries`，老条目不动：

```
covered_upto 之前的内容：不动
covered_upto ~ 本轮：总结成新条目，追加
covered_upto 更新到新位置
```

如果每次都对整段历史重新总结，会有两个恶果：

- 慢且贵
- **内容漂移**：同一段对话总结三次会得出三个版本，越总结越失真

---

## 七、读档流程

```
1. 读 memory.enabled
2. false / 不存在 → 全量发送 messages（现状）
3. true →
   a. 从 messages 末尾往前取，直到估算达到 8000 token
   b. 起点向前对齐到最近的「用户消息」
   c. 组装：人设 + 世界书 + entries + 最近段 + 本轮输入
```

**注意**：回想界面读的是 `messages`，与裁剪无关，**前端一行都不用改**。

---

## 八、检索：现在不做

「最近段 + 全部条目」这个组合能撑很久——几十条记忆才几百 token。

真正需要检索是**条目多到带不动**时（> 200 条 / > 4K token）。到那时再加：

```
玩家每说一句 → 用这句去检索 top-5 相关条目 → 注入
```

**先别做 RAG。** 先把「摘要 + 全带条目」跑通，能解决 90% 的问题。

---

## 九、兜底：查不到的时候不要编

最危险的不是「记不住」，是**记不住还硬编**。

系统提示里必须明确：

> 如果记忆里没有相关内容，用模糊的方式带过（「记不太清了」），
> **不要编造具体细节**。

角色扮演里「她记不清了」完全合理，甚至更像人；**编造才是毁灭性的**——玩家一旦发现她编，信任就崩了。

---

## 十、实现顺序（按风险从低到高）

**第一步：加数据结构**

- 存档写入时加 `memory` 空字段（`enabled: false`）
- 读档逻辑完全不变
- 验证：旧存档能读、新存档能读、回想正常

**第二步：加 token 估算 + 裁剪**

- 实现估算函数
- 读档时按阈值判断，超了就只发最近段
- 此时 `memory.enabled` 仍是 false，条目为空
- 验证：超长存档能载入、剧情连贯

**第三步：加摘要生成**

- 存档后异步生成条目
- 读档时把条目注入 system 提示
- 验证：条目内容合理、生成失败能降级

---

## 十一、验收标准

| 项 | 标准 |
|---|---|
| 前端 | **零改动**，回想能翻到全部原文并可选 |
| 兼容 | 旧存档（无 `memory` 字段）正常读取 |
| 健壮 | 摘要生成失败时，存档正常、读档正常 |
| 成本 | 载入超长存档时，发送 token 不超过阈值 |
| 连贯 | 读档后问「我们刚才在聊什么」，回答与最近段一致 |

---

## 十二、留给实现者的三个判断

1. **阈值触发点只在读档时判断**，不要在对话中途切换——中途切换玩家会觉得「她忽然失忆」
2. **记忆条目里务必留一条「当前剧情进展」**，2~3 句说清「刚发生到哪儿了」，优先注入
3. **`from` 区间要存**，出问题时能回溯是哪几条消息总结错了

---

## 附：为什么这个设计值得做

它让存档变成两层：

- `messages` 是**日记**（完整、可回看）
- `memory` 是**印象**（压缩、供模型使用）

玩家读档回来的感觉会从「她有一份聊天记录」变成「她记得我这个人」。

而且这套机制对玩家不可见——不弹「为节省上下文已折叠」，不显示「记忆条目生成中」。

**折叠是工程语言，记忆是人话。**
