## 一、缘起与目标

目标只有一句话：**做一个 QQ 聊天窗口样子的桌面程序，对面是冬马和纱。**

但要"像"，就意味着不能只调个 API 套个白底对话框。和纱得有：

- 游戏原版的界面（对话框、选项、存档、回想）
- 原作的立绘，按情绪换
- 她说日语，配音是原作声优的风格
- 下面的对话框显示中文对照
- 人设不能崩——她是嘴硬心软、傲娇、钢琴天才、不擅长表达感情的那种人

这五条要求决定了整个技术路线：**素材必须从游戏本体里挖，对话交给云端模型。**

## 三、界面：一场持续几十轮的像素级拉锯

这一段是整个项目里最失败的部分，值得单独写。

### 3.1 舞台坐标系

程序用 pywebview 开一个 1280×720 的无边框窗口，里面装一个 `800×450` 的舞台 div，用 CSS transform 等比放大：

```js
const k = Math.min(innerWidth / 800, innerHeight / 450);
stage.style.transform = `scale(${k})`;
```

所有 UI 元素必须用**舞台坐标**（800×450 的像素）绝对定位。游戏截图是 2730×1536，换算系数：

```
2730 / 800 = 3.4125
```

这条换算关系在文档里出现很多次，因为**几乎所有错误都源于没守住它**。

### 3.2 错误的开始：两套坐标混用

第一版设置界面，我把 PAGE 和 OPTION 标签按"1280 坐标"写进 CSS：

```css
#optPageTxt { left: 640px; }   /* 640 是 1280 坐标下的位置 */
#optT1      { left: 675px; width: 187px; }
```

但舞台只有 800 宽。`675 + 187 = 862 > 800`，第三个标签直接顶出屏幕。

**教训一：一个界面里只能有一套管坐标系。** 混用不会报错，只会"看起来怪怪的"，然后你会怀疑人生。

### 3.3 修正后的第二个错误：`position:fixed` 在 transform 里

把界面挪进舞台后，我用了一个包裹 div 加 `transform: scale()`，结果所有 `position: fixed` 的子元素都相对那个 div 定位，整个界面缩成一团。

**教训二：`transform` 会创建新的包含块。** 在被 transform 的祖先里面，`fixed` 不再相对视口。

### 3.4 第三个错误：元素逐个定位

放弃包裹层后，我把每个元素单独绝对定位：

```css
.optLogo    { left: 26px;  top: 28px;  width: 171px; }
.optPageTxt { left: 640px; top: 90px;  width: 48px; }
.optPageBar { left: 636px; top: 70px;  width: 644px; }
```

每个数字都是从截图里量的。但**每个元素都是独立测量的，误差会累积**：PAGE 偏 5px、标签偏 8px、箭头偏 12px，整排看起来就散了。

**教训三：一排相关的元素要么整行合成一张图，要么共享同一个容器原点。** 分别定位等于把对齐的责任交给每一行 CSS。

### 3.5 第四个错误：从参考图里裁像素

走投无路时我试了直接从参考截图里裁像素：

```python
im.crop((1370, 150, 2730, 232)).save("tabrow_bg.png")
```

问题是**截图里的背景也一起被抠进去了**。贴到我们偏暗的背景上，出现一块明显偏亮的方块，"格格不入"。

而且标签行的截图里已经包含了三个标签，我又在上面叠了一层标签图，直接重影。

**教训四：从截图里裁切只适合纯静态、背景干净、且你不打算在上面叠任何东西的区域。** 这个条件的实际命中率极低。

### 3.6 最后的诊断：给每个元素画红框

反复失败之后，我加了一段调试 CSS：

```css
#optScreen .optLogo, #optScreen .optPageTxt, #optScreen .optPagerTxt,
#optScreen .optArrow, #optT1, #optT2, #optT3 {
  outline: 1px solid red !important;
}
```

然后让用户截图。这一张图立刻暴露了三类问题：

```
1. 标签宽度全部偏大（设了 120，实际量出游戏是 117 / 96.7 / 95.2）
2. 翻页文字按素材原尺寸绘制，没吃 CSS 的 width
3. 位置整体偏了 60px 左右
```

**教训五：看不清真实渲染时的微调都是赌博。** 加个红色描边、导出一张调试截图，比改十次 CSS 都快。

### 3.7 结局

设置界面和特别模式界面，反复十几轮仍然对不齐。最后按用户要求**删掉这两个界面**，只保留主菜单上的按钮。

主菜单五项：

```
开始游戏 / 继续游戏 / 系统设置 / 特别模式 / 结束游戏
```

其中"系统设置""特别模式"点了没反应——这是妥协，写在 README 的"已知取舍"里。

**这是这个项目最大的教训：当一件事反复失败五次以上，问题多半不在执行细节，而在方法本身。** 我应该更早停下来做调试工具，而不是继续改数字。

## 四、字体：891 个字的图集

游戏的中文是补丁自带的字体——`sub_frame.tga` 里排着 891 个字形，程序按字查表、裁格子、拼图。

我们复用了这套机制：

```
sub_render.render_block(text) → PNG bytes
```

对于图集里没有的字，回退到系统 `msyh` 27px。

这样做的好处是：对话框里的字和游戏**完全同源**，笔画粗细、字距、抗锯齿都一样。用普通 web 字体永远差一口气。

代价是：所有文本都得走后端渲染成图片，前端不能直接用 DOM 文字。所以对话气泡是一张一张 PNG 贴上去的。

## 五、语音：GPT-SoVITS 与社区权重

用 GPT-SoVITS v4 做 TTS，音色权重用第三方作者公开分享的模型（本项目只做调用方）：

```
GPT 权重    GPT_weights_v4/<音色名>-e15.ckpt
SoVITS 权重 SoVITS_weights_v4/<音色名>_e8_s33072_l32.pth
参考音频    自备（一段干净的干声，10 秒左右）
参考文本    参考音频对应的日文原文
```

权重是第三方作者训练并公开分享的，本项目不训练、不转存、不再分发；
仓库里没有任何音频文件，参考音频需要使用者自己准备。

服务跑在 `:9880`，程序通过 `tts_client.py` 调用。用 `tts/GPT-SoVITS/runtime/python.exe` 启动，避免和主程序的 venv 打架。

**教训九：TTS 的参考音频决定音色。** 同一套权重换个参考音频，出来的气质完全不同。选参考音频比调参数重要。

## 六、翻译：本地 1.8B 模型

她说日语，下面的对话框要显示中文。用 Hy-MT2-1.8B（Q4_K_M，llama.cpp）：

```
模型  tts/models/Hy-MT2-1.8B-Q4_K_M.gguf
端口  9881（可开 9881~9884 四个实例）
延迟  单条约 0.3 秒
```

**关键发现：这个服务内部有全局锁，并发请求会排队。** 8 线程打一个端口，吞吐和单线程一样。要并行只能多开端口：

```python
PORTS = [9881, 9882, 9883, 9884]
port = PORTS[n % len(PORTS)]
```

批量翻译时，四个端口跑满约 150 条/分钟。

**教训十：并发不是加线程就有用。** 先看服务端有没有锁。

## 七、为什么用云端模型

早期也试过在本地跑小参数模型，语气和连贯性都达不到要求（沉默、跑题、崩人设）。最后放弃本地路线，改用云端 API。

> 说明：本项目**没有训练过任何模型**——不涉及训练数据构造，也不涉及在游戏剧本上做微调。
> 这一节只讨论"用哪个云端模型、怎么把它调教得像和纱"。

### 8.1 两个云端方案对比

| | deepseek-flash | deepseek-v4-pro |
|---|---|---|
| 沉默率 | 0% | 0% |
| 上下文连贯 | 好 | 好 |
| 语气准确度 | 高 | 高 |
| 带动作 | 16% | 0% |
| 25 轮成本 | $0.015 | $0.055 |
| 延迟 | ~1.5 秒 | ~2 秒 |

同样问"我能坐旁边听吗"：

```
flash： 「好きにすれば。…でも近すぎんなよ、集中できなくなる」
pro  ： 「…邪魔するなよ。それだけ守るなら、そこにいるくらいは許す」
```

两个都合格，flash 更爱带动作、更便宜，所以默认用 flash。

### 8.2 成本核算

用官方价目表（每百万 token，美元）：

| | deepseek-flash | deepseek-v4-pro |
|---|---|---|
| 输入（缓存未命中）忙时 | 0.30 | 1.32 |
| 输入（缓存命中） | 0.006 | 0.044 |
| 输出 忙时 | 1.20 | 3.96 |

25 轮对话累计输入 4.2 万 token（每轮都带完整历史），输出约 2 千 token。

按每天 500 轮估：

```
无缓存：约 $0.28/天
有缓存：约 $0.09/天（人设 + few-shot 是固定前缀，命中率很高）
```

**一天几毛钱人民币。**

### 8.3 决定

```
对话   → 云端（deepseek-flash）
翻译   → 本地（Hy-MT2）
语音   → 本地（GPT-SoVITS）
```

云端只管"说什么"，本地管"怎么翻译、怎么念"。

### 8.4 few-shot 的设计

21 组示例，来自游戏台词与人设，要求：用户侧必须是中文、双方都不超过 90 字。

```
带 <action> 的    6 组
普通台词          12 组
短句（≤20 字）     3 组
```

外加两条硬约束写进 system：

```
【语言】无论对方用什么语言说话，你都只用日语回答。
【格式】只输出你要说的话。如果有动作或表情，必须写成
        <action>（…）</action> 放在台词前面，不允许裸描写。
```

不加语言约束时，25 轮里有 10 轮飘成中文；加上之后 25/25 全是日语。

**教训十一：few-shot 管风格，system 管规则。** 语言、格式这类硬要求必须写在 system，不能指望示例带出来。

## 八、最终架构

```
┌─────────────────────────────────────────────┐
│  pywebview + WebView2（1280×720 无边框）      │
│                                             │
│  800×450 舞台 ──── transform: scale ────▶   │
│    ├─ 标题画面 / 对话画面 / 存档 / 回想       │
│    ├─ 立绘（278 张，按情绪切换）              │
│    └─ 对话框（图集字形渲染成 PNG）            │
└───────────────┬─────────────────────────────┘
                │ HTTP 127.0.0.1:8771
┌───────────────▼─────────────────────────────┐
│  Python 后端（main.py）                      │
│    /api/chat    → 云端对话 + 拆分 action      │
│    /api/text    → 图集字形渲染               │
│    /api/tts     → 本地语音                   │
└───────────────┬─────────────────────────────┘
                │
   ┌────────────┼──────────────┐
   ▼            ▼              ▼
deepseek     Hy-MT2        GPT-SoVITS
(云端)       :9881         :9880
```

### 关键实现

**动作拆分**（`main.py`）

```python
ACTION_RE = re.compile(r"<action>\s*(.*?)\s*</action>", re.S)

def split_action(text):
    acts = ACTION_RE.findall(text or "")
    rest = ACTION_RE.sub("", text or "").strip()
    return acts, rest
```

动作送翻译 → 显示在"思考"面板；台词送翻译 → 对话框 + 语音。

**配置外置**（`最新版/config.json`）

```json
{
  "provider": "deepseek",
  "base_url": "https://api.deepseek.com",
  "api_key": "sk-...",
  "model": "deepseek-flash"
}
```

放在 exe 同目录，改 key 或换模型不用重新打包。留空则回退到本地 ollama。

**缓存穿透**（每次构建前重打时间戳）

```python
v = time.strftime('%m%d%H%M%S')
s = re.sub(r'opt\.css\?v=[^"]+', 'opt.css?v=' + v, s)
```

WebView2 会按 URL 缓存 CSS/JS。文件名不变时改了内容也不生效——这个坑让界面调优浪费了至少三轮。

## 九、踩过的坑（按痛苦程度排序）

### 1. 界面反复对不齐（十几次迭代）

根因是**两套坐标系混用**，但症状表现得像"每个元素都偏一点"，误导我去逐项微调。

正确做法：先加调试描边，用截图确诊，再动手。


以为 `max_memory` + CPU 卸载能跑长序列。实测无效，因为激活值不跟着走。

正确做法：先用 `probe` 阶段跑 2 步，量出显存和速度，再决定 max_len。

### 4. WebView2 缓存

改了 CSS 看不到变化，以为改错了，实际是读了缓存。

正确做法：构建时给所有静态资源打时间戳。

### 5. 参考图裁切

图干净、位置对、但背景一起抠了，贴到别处就"格格不入"。

正确做法：能用图集素材就用图集素材；非要用截图，先做亮度键控去背景。

### 6. 翻译服务的全局锁

8 线程打一个端口，吞吐和单线程一样。

正确做法：多开端口，一个端口一个实例。

### 7. 人设太长

1,196 字的人设吃掉 864 token，对话窗口只剩一半。

正确做法：人设控制在 300 token 以内，细节交给 few-shot。

### 8. 语言漂移

中文用户 + 日语回复，模型会自己切换语言。

正确做法：system 里写死语言约束，few-shot 全部用目标语言。
