## 一、存档 / 读档

### 现状

界面是**能打开、能点、能写 localStorage** 的，但存的东西和读回来的东西都不对。

`ui2/screens.js` 现在做的事：

```js
// 存档：只存了缩略信息
const data = {
  date: "2026/10/30 23:50",
  text: 最后一句台词的摘要,
  thumb: 立绘的 dataURL
};
localStorage.setItem("wa2_slots", JSON.stringify(all));
```

问题：

- **没存对话历史**。`window.__history` 从来没被写进存档
- **读档不会恢复上下文**。点已存的槽位只是重绘列表，`__history` 不变
- **数据在 localStorage**，换机器就没了；localStorage 有 5 MB 上限，长对话塞不下

所以现在的存档严格讲是个**带缩略图的占位符**。

### 计划的设计

> 「点击存档存储本次对话，读档的话就会把这段对话作为上下文让 AI 再次从这个点开始聊。」

也就是：**存档 = 对话快照，读档 = 恢复上下文继续聊**。

具体行为：

```
存档
  点空槽 → 把当前完整的 window.__history 写进去
  点已有槽 → 覆盖（要二次确认）

读档
  点已有槽 → 把 messages 灌回 window.__history
            → 恢复立绘、背景、BGM 到存档时的状态
            → 对话框重绘成存档时的最后几句
            → 之后发消息时，这些历史作为上下文一起发给模型

删除
  长按 / 右键槽位 → 清空该槽
```

关键点：**读档不是"重新开始"，是"接着上次聊"**。所以存的是完整的 `messages` 数组，不是摘要。

### 涉及的位置

| 位置 | 要改什么 |
|---|---|
| `ui2/screens.js` | `writeSlot()` 加入 `messages`；点击槽位时调用恢复函数 |
| `ui2/game.js` | 新增 `restoreFromSave(data)`：灌 `__history`、重绘、恢复立绘/BGM |
| `app/main.py` | 新增 `POST /api/save`、`GET /api/save/list`、`GET /api/save/{id}` |
| 新增 `app/storage.py` | 文件存储（见下） |

### 实现要点

**1. 存储位置：文件，不用 localStorage**

```
<exe 同目录>/saves/
  slot01.json
  slot02.json
  ...
  auto.json        自动存档（每 10 轮写一次）
```

理由：localStorage 5 MB 上限，长对话（几十轮 + 中文 + 日文）很容易超；文件还能跨机器拷贝。

**2. 存档格式**

```json
{
  "version": 1,
  "saved_at": "2026-10-30T23:50:12",
  "model": "deepseek-flash",
  "messages": [
    {"role": "user", "content": "今天放学挺早的"},
    {"role": "assistant", "content": "「…そうか」",
     "reply_zh": "…这样啊", "action_zh": ""}
  ],
  "scene": {
    "bg": "bg_music.png",
    "sprite": "kaz_casual_01.png",
    "bgm": "bgm_calm.ogg"
  },
  "preview": {
    "date": "2026/10/30 23:50",
    "text": "「…そうか」",
    "thumb": "data:image/png;base64,..."
  }
}
```

`messages` 是原样保存的——包括中文译文，这样读档后对话框能直接还原，不用重新翻译。

**3. 读档后的行为**

```js
function restoreFromSave(d) {
  window.__history = d.messages.slice();
  setBg(d.scene.bg);
  setSprite(d.scene.sprite);
  setBgm(d.scene.bgm);
  // 对话框只重绘最后 3 轮，避免刷屏
  d.messages.slice(-6).forEach(m => addHistory(m.role, m.content));
}
```

注意：**读档不重放语音**。否则一读档就念一串。

**4. 潜在问题**

- 上下文长度：存了 50 轮，读档后继续聊，每次请求都带 50 轮历史 → 输入 token 暴涨（成本按输入计）
  → 解决：读档时只保留最后 N 轮（比如 20 轮），更早的压成一段摘要
- 模型切换：存档里记录了当时的模型，换模型读档可能导致语气不一致
  → 解决：读档时提示"这条存档是用 deepseek-flash 存的，当前是 v4-pro，继续吗？"

screens.js          存档/读档/删除        ~120 行

## 五、按键音效

### 现状

`ui2/assets/snd/` 里有 **64 个音频文件**，`game.js` 里也有 `playSE(name)` 函数，但**几乎没有地方调用它**。

具体问题：

```js
function playSE(name) { ... }   // 函数写好了
document.querySelectorAll(...)  // 但点击按钮时没调
```

现在点菜单、点存档槽、翻页、开关面板——全是静音。唯一有声音的是 BGM 和语音。

### 为什么没做

游戏原版的音效 ID 是硬编码在可执行文件里的，`snd/` 目录里的文件名（`click_01.ogg`、`ok.wav`…）和实际的「哪个动作播哪个音」对不上。64 个文件里能确定用途的不到 10 个。

### 计划的设计

按交互点逐个挂，不追求和原版一一对应：

| 交互 | 音效文件 | 说明 |
|---|---|---|
| 菜单项悬停 | `snd/hover_*.ogg` | 轻微「嗒」声 |
| 菜单项点击 | `snd/click_*.ogg` | 确认音 |
| 存档槽点击 | 同上 | 复用确认音 |
| 翻页（存读档 / 设置） | `snd/page_*.ogg` | 翻页声 |
| 对话框打字 | `snd/type.ogg` | 每 3 个字符播一次，避免过密 |
| 打开 / 关闭浮层 | `snd/open.ogg` / `snd/close.ogg` | |
| 报错 | `snd/error.ogg` | 连不上模型时 |

### 涉及的位置

| 位置 | 要改什么 |
|---|---|
| `ui2/game.js` | `playSE()` 调用点补齐；打字音用节流 |
| `ui2/screens.js` | 存档槽、翻页按钮绑音效 |
| `ui2/menubar.js` | 菜单项悬停 / 点击绑音效 |
| `ui2/config.js` | 加 SE 音量偏好（现在只有 BGM） |

### 实现要点

```js
// 音效池：避免高频点击时互相打断
const SE_POOL = {};
function playSE(name, volume = 0.6) {
  if (!prefs.seOn) return;
  const n = 3;                       // 每种音效 3 个实例轮转
  SE_POOL[name] = SE_POOL[name] || [];
  if (SE_POOL[name].length < n) {
    const a = new Audio("assets/snd/" + name);
    a.volume = volume;
    SE_POOL[name].push(a);
  }
  const a = SE_POOL[name].find(x => x.paused) || SE_POOL[name][0];
  a.currentTime = 0;
  a.play().catch(() => {});
}
```

打字音要**节流**，否则每字一声太吵：

```js
let lastType = 0;
function typeSE() {
  const now = performance.now();
  if (now - lastType > 90) { playSE("type.ogg", 0.25); lastType = now; }
}
```

### 工作量估计

把 64 个文件听一遍挑出可用的（约 1 小时）＋ 挂 7 个交互点（约 2 小时）。

## 七、窗口拖动迟滞

### 现状

**拖标题栏移动窗口时明显卡顿**，拖影跟不上鼠标。

### 原因

窗口现在用的是 CSS 的 `-webkit-app-region: drag`：

```css
.menubar { -webkit-app-region: drag; }
```

WebView2 的这个机制**不是实时的**：鼠标移动事件要经过渲染进程 → 主进程 → `SetWindowPos`，每帧都有额外开销，快速拖动时窗口会落后于指针。

另一个历史原因：之前为了修「拖滚动条滑块会把整个窗口拖走」，把 pywebview 的 `easy_drag` 关掉了（`easy_drag=False`），所以只能靠 CSS 区域拖拽，问题更明显。

### 计划的设计

三条路，按推荐顺序：

**方案 A：恢复 `easy_drag`，精确排除不可拖区域**

```python
window = webview.create_window(..., frameless=True, easy_drag=True)
```

```css
#historyScroll, #hsThumb, input, button, .optT, .slot { -webkit-app-region: no-drag; }
```

pywebview 的 `easy_drag` 走的是原生窗口拖动（和系统标题栏同级），比 CSS 区域拖拽跟手得多。代价是 `no-drag` 必须列全，漏一个就会误拖。

**方案 B：自绘拖动 + 原生移动**

鼠标按下标题栏时记录偏移，`mousemove` 里调用 `/api/window?action=move`，后端用 `window.move(x, y)`：

```js
document.addEventListener("mousemove", e => {
  if (!dragging) return;
  fetch(`/api/window?action=move&x=${e.screenX - dx}&y=${e.screenY - dy}`);
});
```

问题：每次 mousemove 一次 HTTP 请求，延迟比方案 A 大，不推荐。

**方案 C：Win32 消息接管**

用 ctypes 给窗口加 `WM_NCHITTEST` 处理，让标题栏区域返回 `HTCAPTION`，交给系统原生拖动：

```python
user32.DefWindowProcW.argtypes = ...
# 在 WndProc 里：if 命中标题栏: return 2 (HTCAPTION)
```

最丝滑，但要 hook 消息循环，和 pywebview 的窗口过程打交道，属于「能做成但容易出玄学问题」。

### 涉及的位置

| 位置 | 要改什么 |
|---|---|
| `app/main.py` | `create_window` 的 `easy_drag` 参数 |
| `ui2/menubar.css` | `no-drag` 区域列表 |
| `ui2/game450.css` | 滚动条、输入框的 `no-drag` |

### 验证方法

拖动时看窗口边缘和鼠标是否同步：

```
慢速拖（10 cm/s）  应完全同步
快速拖（50 cm/s）  允许 1-2 帧延迟，不应有拖影分离
```

### 工作量估计

方案 A：改两行 + 补 `no-drag` 清单，**半小时**，风险低。
方案 C：半天到一天，风险中。

## 八、立绘与背景 CG 的切换

> **2026-11-02 更新**：背景这一块已经做了 —— `src/scene_cg.py` 按 `<scene>` 标签
> 匹配 `assets/cg/` 里的 119 张场景图（文件名即标签，还认时段），
> 用法见 `场景CG系统.md`。下面「现状 / 计划」写的是做之前的启发式方案，留作背景；
> **立绘服装映射、CG 叠层、出场退场仍然没做**。

### 现状

立绘能换，背景能换，但**切换逻辑是启发式的，不是按剧本来的**。

现在的做法：

```js
function detectScene(text) {          // 从对话文本猜场景
  if (/音乐室|钢琴/.test(text)) return "music";
  if (/天台/.test(text)) return "roof";
  ...
}
function setSpriteByScene(scene) {    // 场景 → 服装
  ...
}
```

问题：

- **靠关键词猜**，用户说「我们上次在音乐室」就会切场景，即使当前不在那儿
- **CG 完全没接**：游戏里很多关键场景会播全屏 CG，现在只有背景图
- 切换是**瞬切**，游戏原版有淡入淡出
- 立绘没有「出场 / 退场」概念，一直显示
- 服装（校服 / 便服 / 冬装）只按情绪挑，没按剧情进度

### 计划的设计

**1. 场景表替代关键词**

建一张表，把每个场景的要素捆在一起：

```json
{
  "music_room": {
    "bg": "bg_music.png",
    "bgm": "bgm_calm.ogg",
    "sprites": {
      "default": "sprites/uniform/kaz_uniform_01.png",
      "angry":   "sprites/uniform/kaz_uniform_angry.png"
    },
    "cgs": ["cg_012.png", "cg_013.png"]
  }
}
```

**2. 由模型决定场景，不由前端猜**

对话请求的返回里加一个字段（和 `<action>` 一样由模型输出）：

```
<scene>music_room</scene>
```

前端读到就切场景；读不到就保持当前场景。这比关键词可靠得多——模型看得到整段上下文。

**3. CG 层**

背景之上、立绘之下加一层 `<img id="cgLayer">`：

```
背景（bg_*.png）
  └─ CG（全屏，播完淡出，或一直显示直到切场景）
      └─ 立绘（278 张）
          └─ 对话框
```

CG 触发条件：场景表里配了 `cgs`，且当前对话轮次到达某个阈值（或者由模型用 `<cg>cg_012</cg>` 指定）。

**4. 转场**

```css
#bgLayer, #cgLayer, #sprite { transition: opacity .35s ease; }
```

切换时先把新图 opacity 设 0 再设 1，避免闪白。

**5. 立绘的出场 / 退场**

`<sprites>none</sprites>` 表示这一轮她不在画面里（比如旁白、换场）。前端据此淡出立绘。

### 涉及的位置

| 位置 | 要改什么 |
|---|---|
| 新增 `ui2/assets/scenes.json` | 场景表 |
| `ui2/game.js` | `detectScene()` 删除，改成读 `<scene>` 标签；新增 CG 层控制 |
| `ui2/game450.css` | `#cgLayer` 样式与转场 |
| `app/main.py` | system 里加一条：允许输出 `<scene>` / `<cg>` 标签 |
| `ui2/index.html` | 加 `<img id="cgLayer">` |

### 实现要点

**标签解析要和 `<action>` 共用一套**

```python
ACTION_RE = re.compile(r"<action>(.*?)</action>", re.S)
SCENE_RE  = re.compile(r"<scene>(.*?)</scene>", re.S)
CG_RE     = re.compile(r"<cg>(.*?)</cg>", re.S)
```

`main.py` 里统一剥掉这些标签，再分别放进返回字段，前端就不会把标签念出来。

**别让模型滥用**

system 里要写清楚：「只在明确换场景时输出 `<scene>`，大多数时候不输出」。否则每句都切场景。

### 工作量估计

场景表整理（18 套服装 × 若干场景）：**1 天**，主要是翻剧本对场景。
代码部分：**1 天**（标签解析、CG 层、转场）。

## 九、上下文限制的用户可调界面

> 用户原话见 `需求原文_两个待完成版块.md`。

> **状态：只记录，不做。** 用户 2026-11-01 明确说「先记下来，之后再做」——
> 而且强调了三遍"不是现在做"。

### 现状

上下文预算全写死在 `program/src/memory.py` 的 `DEFAULTS` 里：

```python
"cloud_ctx": 32000, "local_ctx": 4096,   # 模型能吃多少
"trigger_ratio": 0.6,                    # 吃满 60% 就切记忆书
"recent_ratio": 0.25,                    # 「最近一段」占多少
```

想改只能动代码，或者自己写一个 `program/memory.json` 覆盖（这个文件默认不存在，
但代码里已经支持了）。

**为什么这是个问题**：用户自己用的是云端模型（上下文很大），根本不会碰到；
但别人拿去配本地小模型（4K / 8K 上下文）就会踩——阈值按云端算，一跑就超。

### 计划的设计

在设置界面里加一栏（放 OPTION 2 还是模型管理页待定），能调：

- 模型上下文大小
- 触发比例（默认 60%）
- "最近一段"占多少
- 每几轮重新打包记忆

**关键：调整时要有参考值。** 光给输入框没人知道该填多少，所以旁边要实时显示：

```
你最近 20 句平均每轮消耗 ≈ 320 token
按当前设置（32000 × 60%），大约还能聊 60 轮才开始折叠
```

### 涉及的位置

| 位置 | 改什么 |
|---|---|
| `memory.py` | `DEFAULTS` / `cfg()` 改成从 prefs 读 |
| `main.py` | 新增 `GET/POST /api/memory/cfg`（或并进 `/api/prefs`） |
| `config.js` | 存进 `prefs.json`（已有现成机制） |
| `opt.js` / 新界面 | 数字输入 + 实时参考值显示 |

### 实现要点

1. **估算函数已经有了**：`memory.est_text / est_messages`（中日文约 1 字 1 token，
   其它 4 字符 1 token，×1.05 余量）。要补的是"统计口径"：
   用**最近 N 条的真实估算均值**，别用固定常数——一句"嗯"和一句两百字的差别太大。
2. 改完阈值要**立刻生效**：`memory.cfg()` 每次调用都重新读，不要缓存到变量里。
3. 运行时记忆书里的 `covered` 不用清：阈值变小只会让窗口变短，不影响已总结的部分。
4. 界面上的"还能聊 N 轮"是估算，**标注"约"**，别让用户当精确值。

### 工作量估计

接口 + 设置项 + 显示参考值：**半天**。

## 十、角色配置界面

> 用户原话见 `需求原文_两个待完成版块.md`。

> **状态：只记录，不做。** 同一轮记录，用户说"这两个现在都不做"。

### 现状

角色是**写死的**：名字"和纱"在 `game.js` / `index.html` / 后端一共出现 22 处
（对话框左上角 `#namePlate`、回想列表、存档末句、`persona*.txt`、`fewshot.json`、
`worldbook.json` 全都有）；立绘按场景 + 情绪从 `res/assets/char/` 取；
提示词在 `persona/` 的两个 txt；世界书在 `worldbook/worldbook.json`；语音参考音频在 `tts_client.py` 的 `REFS`。

想换一个角色，得改一堆散落的文件。

### 计划的设计

一个「角色管理」界面，一份角色一个目录，可配置：

| 项 | 说明 |
|---|---|
| **角色名称** | 对话框左上角显示的人名；回想、存档末句里的称呼也跟着变 |
| **立绘** | 选一个立绘目录 + 场景 / 情绪 → 图的映射 |
| **提示词** | 文本框，对应现在的 `persona/persona.txt` / `persona/persona_core.txt` |
| **世界书** | 条目编辑（关键词 / 内容 / 优先级），对应 `worldbook/worldbook.json` |
| **记忆书（常驻）** | **注意：和刚做的"对话记忆书"是两回事**，见下 |
| **语音参考音频** | 选文件夹，按情绪分配 wav + 对应文本 |

#### 两种「记忆书」的区别（必须分清）

> **2026-11-02 更新**：常驻记忆书**已经接线**（特别模式的「记忆书」导入 → `char/memory/`，
> 每轮作为角色固定设定注入）；对话记忆书这边也简化了：读档把存档里的记忆书复制进
> `cache/memory_runtime.json`，之后只读缓存，存档只做快照（不再在存档时跑总结）。
> 两者在 system 里的措辞已经分开（「你记得的旧事」vs「你记得的事」）。

| | 常驻记忆书（这个界面里配的） | 对话记忆书（已实现） |
|---|---|---|
| 内容 | 用户手写的角色背景 / 关系 / 既定事实 | 由历史对话自动压缩出来的短句 |
| 什么时候注入 | **每次启动 / 每次对话都注入** | 只在历史超过阈值时 |
| 什么时候生成 | 用户编辑，不自动生成 | 存档时 / 每 N 轮自动生成 |
| 会变吗 | 不变（除非用户改） | 会随对话增长 |

三者（常驻记忆书 → 世界书 → 对话记忆书）在 system 提示里的**顺序和措辞要分开**，
否则模型会把"角色设定"和"这次聊过的事"混成一锅。

#### 语音参考音频

GPT-SoVITS 需要**参考音频 + 参考文本配对**（音色由模型定、语气由参考定）。
现在的 `REFS` 是四个情绪指向同一个 wav + 同一句文本。

界面里要做的是：选文件夹 → 列出 wav → 每个情绪挑一条 → 填对应的参考文本。
选文件夹要用 pywebview 原生的 `create_file_dialog`（浏览器 `<input type=file>` 拿不到
真实路径，而 GPT-SoVITS 需要路径）。

### 涉及的位置

| 位置 | 改什么 |
|---|---|
| `main.py` | `persona_text()` / `load_worldbook()` 改成读当前角色目录；新增 `/api/character` |

### 实现要点

1. **名字先收口**：现在 22 处硬编码，做界面之前先把名字收敛成"一个地方提供"，
   否则改了名字总有几个角落还是"和纱"。

### 工作量估计

角色配置界面 + 数据迁移（把现有 persona/worldbook 搬进角色目录）+ 名字收口：
**2~3 天**；语音参考音频选择：**半天**（主要是配对文本的处理）。
