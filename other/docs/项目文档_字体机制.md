# 中文字体机制：调查记录与结论

> 记录时间：2026-10-29
> 目的：搞清楚游戏中文是怎么渲染的，以及我们能不能直接复用

---

## 一、汉化组用的方案（已查明）

游戏本体是日文，引擎用自己的位图字模渲染文本。汉化组并没有修改 exe，而是做了两件事：

### 1. 换剧本：假 SJIS

`ck-gal.pak`（4.63 MB）里是 379 个条目、182 个中文剧本 `.txt`，总字符数 **1,842,394**。

但文件里的字节不是 GBK，而是 **Shift-JIS 双字节码**，例如：

```
81 63 81 76 2c 95 ff ba 88 df 81 43 ...
```

`81 63`、`81 76` 是 SJIS 码位。也就是说，**汉字被塞进了 SJIS 的码位里**。

### 2. 换字模：码位上的字形变成汉字

把游戏自带的 `fnt.pak` / `fon.pak` 替换成"码位不变、字形换成汉字"的版本。

这样引擎照常按 SJIS 解码 → 拿到码位 → 从字模取图形，取出来的就是汉字。

**关键：没有"换字形的代码"。** 整套机制就是"换文件"，查表逻辑在 `WA2.exe` 引擎内部，没有对外接口。

## 二、本地资源盘点

| 文件 | 内容 | 数量 | 用途 |
|---|---|---|---|
| `fnt.pak` / `fon.pak` | 引擎位图字模（已换汉字） | 11,817 格 | 渲染对话正文 |
| `ck-gal.pak` | 中文剧本（假 SJIS） | 182 篇 / 184 万字 | 对话文本 |
| `subfont.tga` | 汉化补丁的外挂字幕字模 | 890 格 | 语音字幕 |
| `subtext.dat` | 外挂字幕数据 | 45 条 / 293 行 | 语音字幕 |

**注意：`subfont.tga` 和引擎字模是两套不同的东西。**

- `subfont.tga`：反锯齿的微软雅黑，用在屏幕顶部的外挂字幕
- `fnt.pak`：**1-bit 位图**（灰度只有 0 和 255，无抗锯齿），用在对话框正文

## 三、尝试过的方案与结果

### 方案 A：直接复用引擎字模（失败）

思路：把 11,817 格当作字形库，匹配字符后按需取用。

| 检验项 | 结果 |
|---|---|
| 常用字模板匹配（10 个字） | IoU 0.41~0.63，最高分与次高分差 **0.002~0.03** |
| 生僻字对照（靐/齉/龘） | 0.70~0.74，反而比常用字高 |

**结论：匹配等于随机。** 原因是引擎字模是 1-bit 位图，而 TTF 渲染带灰阶过渡，IoU 实际在比"笔画密度"，不是字形。

### 方案 B：反推字节码 → 汉字（失败）

思路：本地剧本是假 SJIS，若能找到码位与汉字的对应，就能解码全部文本。

| 检验项 | 结果 |
|---|---|
| 全量 182 篇统计不同双字节码 | **32,153 个** |
| 字号模格子数 | 11,817 个 |

数量上不可能 1:1 对应，说明字节切分假设有误（`0xFF` 既可能是分隔符也可能是码的一部分），无格式文档无法可靠切分。

**结论：放弃。**

### 方案 C：现有做法（采用）

| 来源 | 覆盖 | 一致性 |
|---|---|---|
| `subfont.tga` 直贴 | 891 个常用字 | 可见像素 **100% 一致** |
| 拟合参数现画 | 其余所有字 | 白芯面积差 **+2%**，字高差 0.6px |

拟合参数（对 836 个汉字做 IoU 全量扫描得到）：

```
字体      微软雅黑 常规
字号      27 px
格子内偏移 (3, -3)
描边      2px 纯黑
格子      32 x 32
每字前进   28 px
填充      纯白 #FFFFFF
```

## 四、为什么"整个机制搬过来"行不通

用户提过：直接把 `ck-gal`、`fnt.pak`、`fon.pak` 和"换字形的代码"整套搬过来。

**问题在于没有代码可搬。**

- 汉化组的做法是"替换文件"，不存在独立的字形替换程序
- 查表逻辑（码位 → 格子）编译在 `WA2.exe` 里
- 没有引擎，那 11,817 格只是一堆**无序的图片**，无法按字符索引

换句话说：搬得走素材，搬不走"查表的人"。

## 五、如果还要继续（唯一可行路线）

**OCR 引擎字模。**

1-bit 位图对 OCR 反而是理想输入（没有抗锯齿噪点）：

1. 把 11,817 格切成单字图片
2. OCR 逐个识别（PaddleOCR / Tesseract）
3. 用已有的 3,171 字中文词表做约束校验

| 项目 | 预估 |
|---|---|
| 切图 | 10 分钟 |
| OCR | 30~60 分钟 |
| 校验 | 20 分钟 |
| 识别率风险 | 70~85%（未知点阵字体） |

**收益**：拿到游戏对话框里真正在用的那套中文位图字形，观感比拟合的微软雅黑更接近原版。

**风险**：识别率不确定，可能一半用不上。

## 六、当前实现

`app/sub_render.py`：

```python
STRICT_FONT = msyh.ttc     # 微软雅黑 常规
STRICT_SIZE = 27
STRICT_DX, STRICT_DY = 3, -3
FONT_OCCUPATION = 32       # 格子
FONT_ADVANCE = 28          # 每字前进
```

渲染顺序：

1. 字在 `subfont.tga` 字符表里 → 直接贴格子（像素级一致）
2. 不在 → 用上面参数现画

覆盖 891 字，其余走兜底。这是目前能拿到的最优解。
