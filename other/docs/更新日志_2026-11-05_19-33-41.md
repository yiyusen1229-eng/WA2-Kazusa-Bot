# 更新日志 2026-11-05 19-33-41

> 主题：**让对话模型自己输出双语**（`<ja>` + `<zh>`），翻译层降级成兜底。
> 起因：用户提出「不如让对话模型直接把中文日文一起输出，它自己写的句子意思更准确」。
> 范围：`api_chat.py`（提示词 + 判路）、`text_parse.py`（`split_bilingual` / `looks_zh`）、
> 自测、文档。

## 一、为什么这个方向对

原来的链路是：模型只出日文 → 再找**另一个模型**翻成中文当字幕。
第二个模型不知道上下文，实测两类错：

| 错法 | 例子 |
|---|---|
| 人名音译错 | `はるき` → 「**春树**」（正确「春希」） |
| 中→日满口敬语 | 「…ではありません」「…ください」，和纱不会那么说 |

模型自己写的时候，它**知道这句话想表达什么**，把意思原样再说一遍就行——同一个上下文、
同一份人设，还不占额外往返。顺带**省掉每轮 1~2 次翻译请求**（上一版刚加了云端翻译，
每条 +0.5~1s，现在这条路不再是常态）。

## 二、改成了什么样

模型一次给四种标签：

```
<emotion>毒舌</emotion><action>（别过脸）</action>
<ja>「べ、別に。あんたのためじゃないから」</ja><zh>「才、才不是。不是为你才做的」</zh>
```

- 提示词【格式】后面加了一段【双语】：`<zh>` 必须是**同一句话**的中文（不许改口、省略、加戏），
  `<action>` 用中文写，并给了一个完整的格式样例（few-shot 示例里没有双语，靠这段补）。
- 后端：`text_parse.split_bilingual()` 拆 ja / zh；`api_chat` 用 **ja → `reply` + `speak_ja`（TTS）**、
  **zh → `reply_zh`（字幕）**。前端契约没变，`wt-chat.js` 不用改。
- 兜底：`<zh>` 缺失或不像中文（`looks_zh()`：有汉字、假名<2）才走 `translate.py`；
  `<action>` 有假名才翻。**模型不听话也不影响玩。**
- 标签容错：`<jp>`、`<cn>`、`<中文>` 这类写法都认，残留标签统一清掉。

## 三、验证

**模型真的会这么输出**（拿真实 system 片段 + 21 条 fewshot + 真 key，3 句各发一次）：

| 场景 | 模型输出（节选） | 解析结果 |
|---|---|---|
| 平常 | `<action>（轻轻拉了一下围巾）</action><ja>「おはよう。本当に寒いな…」</ja><zh>「早上好。真是冷啊…」</zh>` | ja/zh 都拿到，残句为空 |
| 被戳破 | `<emotion>毒舌</emotion><action>（别过脸，语气冷淡）</action><ja>「見てない。あんたの見間違いでしょ」</ja><zh>「没看。你看错了吧」</zh>` | 同上 |
| 生气 | `<emotion>调侃吐槽</emotion>…<zh>「好好好，我知道你讨厌我。所以呢？」</zh>` | 同上 |

3/3 都给了双语，`looks_zh` 判定全为真。

- `tools/test_text_parse.py`：33 → **42 项**（双语块 7 项 + `looks_zh` 3 项）。
- `run_smoke.py`：**35 项全绿**（7.9 秒）。

## 四、代价 / 边界

- **输出 token 变多**（一句日文 + 一句中文），但省掉一次翻译往返，通常**净更快**。
- 历史记录里 `content` 仍存日文原句、`zh` 存模型给的中文；回想界面照旧。
- 老存档/老回复没有 `<zh>`，读档回放时走的是存下来的 `reply_zh`，不受影响。
- `translate.py` 仍然保留（兜底 + 未来别的用途），术语表也还有用
  （兜底路径、以及模型偶尔直接把人名写成中文错的写法时可以纠正）。
