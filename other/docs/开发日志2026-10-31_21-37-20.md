│   ├── 和纱绿色版_v1.zip
│   └── 和纱_v6_字模版.exe

    ├── dev/            game_pak、tts、中间产物

配套脚本：

| 脚本 | 作用 |
|---|---|
| `tools/assemble.py` | src + res → ui2（构建用中间目录） |
| `tools/build_exe.py` | 打单文件 exe |
| `tools/build_portable.py` | 打绿色版 + zip |
| `tools/run_dev.py` | 直接从源码运行（改完即生效） |

**收益**：`program` 永远是"现在的样子"，`release` 永远是"发出去的那一版"，两者不混淆。

## 二、性能与稳定性（本日重点）

### 2.1 卡死的根本原因：js_api 序列化递归

控制台被这样刷屏：

```
[pywebview] Error while processing win.native.AccessibilityObject.Bounds.Empty.Empty.Empty...
```

**原因**：`_api.win = window` 把 pywebview 的 `Window` 对象挂在了 `js_api` 上。
`js_api` 的**公有属性会被序列化并发送给 JS**，而 `Window` 带着完整的原生引用树，
序列化器无法处理 → 无限递归 → CPU 占满 → 卡死。

**修复**：改私有属性（`_` 开头不参与序列化）：

```python
def __init__(self):
    self._window = None      # 不能叫 win

_api._window = window
```

**效果**：内存从峰值 **2902 MB** 降到 **157 MB**，报错刷屏消失。

### 2.2 静态服务加 Range 支持

原来 Python 的 `SimpleHTTPRequestHandler` 不支持 `Range`，浏览器无法跳读视频：

```
修复前：38 MB 视频 → 23~31 秒（约 1.2 MB/s）
修复后：38 MB 视频 → 0.04 秒（约 1000 MB/s）
```

实现了 `send_head()`（解析 `bytes=` 区间、返回 206 + `Content-Range`）
和 `copyfile()`（按区间输出，块大小 64 KB → 256 KB）。

### 2.3 开场视频改为一次性加载

日志里 `opening.mp4` 出现 **31 次 SLOW**，浏览器反复发 Range 请求、反复解码。

```js
fetch(url, { cache: "force-cache" })
  .then(r => r.blob())
  .then(b => { vid.src = URL.createObjectURL(b); vid.play(); })
```

同时把「3 秒没播起来就跳过」的兜底逻辑删掉——那条逻辑在慢速加载时会
**自动跳过开场**，导致没点屏幕也跳了。

### 2.4 高频请求不再写日志

`movepos` / `rect` / `state` 每秒几十次，每条日志都要落盘：

```
修复前：单条 200~260 ms
修复后：1~2 ms
```

### 2.5 字模缓存加上限

`/api/text` 的 `_TEXT_CACHE` 原本无上限，聊得越久越多。改为 **400 条近似 LRU**。

### 2.6 拖动改走 pywebview JS API

原来拖动每帧发一次 HTTP 请求；现在优先调用进程内的 `drag_move()`，HTTP 只作兜底。
