# 更新日志 2026-11-05 19-40-23

> 主题：**回想重播不像重播**——不是因为缓存坏了，是因为重播算错了缓存 key。
> 范围：`ui/wt-backlog.js`、`ui/wt-chat.js`、`index.html`（bump `?v=`）；
> 顺带修掉 `translate.py` 术语表的两处真 bug。

## 一、缓存机制本身没坏

先把证据摆出来（`tts_client.py`）：

```
缓存 key = md5(text | lang | emotion | 参考音频目录签名)
缓存文件 = program/cache/tts/<hash>.wav   （旁边一份 .gain.json 记响度增益）
```

- `program/cache/tts` 现在有 **18 个 wav + 18 个增益侧车**，机制在正常写入；
- 日志里同一句既有 `耗时 0.0s`（**命中**）也有 `耗时 1.0~5.2s`（**重新合成**）；
- 缓存**每次启动清空**是设计行为（#1 的取舍：本次运行有效，退出即弃），不是故障。

所以问题不在「写不进 / 被删掉」，在**重播时算出来的 key 和当初不一样**。

## 二、真因：重播写死了 `emotion=neutral`

```js
// wt-backlog.js（改之前）
fetch("/api/tts?text=" + clean + "&lang=ja&emotion=neutral&speak_ja=" + clean)
```

而正常对话时前端传的是**这句的情绪标签**（日志里 `TTS 准备: lang=ja emo=calm`）。
key 里带着 `emotion`，`calm` 和 `neutral` 是两段不同的音频 —— 于是**每次重播必然 miss**，
老老实实重新合成 1~5 秒。日志里那些「同一句、emo=neutral、每次 2~5 秒」的重复请求就是这么来的。

## 三、改法

| 文件 | 改动 |
|---|---|
| `ui/wt-backlog.js` | `addHistory(role, text, raw, emo)` 多带一个情绪，存进 `row.dataset.emo`；重播用它算 key，**老存档没有 emo 才退回 `emoOf(text)` 猜** |
| `ui/wt-chat.js` | 存历史时把当时的情绪一起写进去（`history[i].emo`），`addHistory` 也传 |
| `ui/index.html` | `wt-backlog.js` / `wt-chat.js` 的 `?v=` bump 到 `202611051939` |

`rebuildBacklog`（读档 / 切角色后重建列表）也跟着传 `m.emo`，所以读档后重播同样能命中。

## 四、顺带修掉的两个真 bug（都是自测抓的）

1. **术语表会自我覆盖**：原来的实现是逐条 `text.replace()`。同时有「春树→春希」和「春→X」时，
   「春树」先变「春希」，紧接着「春」又把里面的「春」换成 X，得到 **「X希」**。
   现在改成**单个正则一遍过**（长键优先），不会级联。
2. **按 mtime 缓存术语表会读到旧内容**：同一秒内改文件，mtime 不变 → 缓存不失效。
   术语表只有几百字节，直接每次读盘，把缓存去掉（翻译结果本身另有缓存）。

`test_translate.py` 连跑三次全绿（之前「长键优先」一项会随机失败）。

## 五、验证

- `node --check wt-backlog.js / wt-chat.js` 通过；`run_smoke.py` **35 项全绿**。
- 重播是否真的快，要在真机上验：重启后打开回想、点重播，日志里那句 TTS 应该是
  `耗时 0.0s`（命中）。**如果还是 2 秒以上**，说明 key 里还有别的变量在变
  （`参考音频目录签名` / `lang`），到时候看 `_tts_cache_path` 的三段。

## 六、边界

- 老存档里的历史没有 `emo` 字段，重播会退回按文本猜情绪 —— 可能偶尔还是 miss，属预期。
- 换了参考音频（导入新 voice）会让所有 key 失效，这是刻意设计（不然换音色还播旧的）。
- 缓存仍在 `program/cache/tts`（不在 `build_env/cache` 下），已被 `.gitignore` 的 `cache/` 覆盖。
