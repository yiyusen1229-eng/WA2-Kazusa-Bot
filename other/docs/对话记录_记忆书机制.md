# 对话记录：上下文裁剪与记忆书机制

> 原始对话，未做任何总结或删改。
> 时间：2026-11-01 下午（德国时间）
> 参与：用户 × 烬

---

## 用户

你说这样的话我的程序会不会也有这个问题呢？随着存档和历史对话越来越长，最终达到上下文上限不得不删除......

## 烬

会，而且是**所有聊天程序都会**——问题不是"会不会遇到"，是"遇到的时候丢掉什么"。

## 常见的几种处理方式

**1. 滑动窗口**（最简单）
只保留最近 N 轮，更早的直接丢。省事，但角色会"忘记"之前发生过的事。

**2. 摘要压缩**
把旧对话让模型总结成一段，替代原文。省 token，但细节会丢，而且摘要本身有偏差。

**3. 检索**（RAG）
不全塞进去，而是每次根据当前话题，从历史里捞出相关的几段。你这个项目里 `story_rag.py` 干的就是类似的事——只不过它检索的是剧情资料，不是聊天历史。

**4. 分层记忆**
- 人设/世界设定：**永远保留**（不长，必须留）
- 长期记忆：关键事件摘要
- 短期记忆：最近 N 轮原文

这是目前效果最好的做法，但也最复杂。

## 你这个项目的特殊之处

普通聊天助手忘点东西无所谓，但**和纱要是忘了你们之前聊过什么，那是"人设崩"**。

所以对你来说，优先级应该是：

```
人设/口吻  >  最近几轮  >  早期对话
```

早期对话可以压缩、可以检索，但**语气和设定一个字都不能丢**。这个顺序如果搞反了（比如为了省内存去砍人设），程序还能跑，但"她"就不是她了。

## 一个挺有意思的联想

你刚才问的那个问题，和我们聊的《可塑性记忆》是同一件事：

> 容量有限，必须删。删什么、怎么删、删了之后还是不是原来那个人。

你做的这个程序，本质上是在**给一个虚构角色安排记忆管理策略**。而这个策略会决定她是个"什么都记得的人"，还是个"每次见面都像初次"的人。

甚至——**失忆本身可以做成剧情**。如果她的记忆真的被压缩过，那不是 bug，是设定：她记得你们的相处，但细节模糊了。这反而比"完美记忆"更像人。

## 用户

那我的思路是这样，当历史对话或者存档记录超出某一个限度的时候，载入存档的逻辑就自动变一下，不是直接让ai接着聊，而是把它作为本轮对话外挂的记忆书，供ai检索读取，你觉得怎么样

## 烬

这个思路我认为是对的，而且比"滑动窗口砍历史"高明一个层级。

不过有几个地方需要定清楚，否则做出来会发现"查不到"的时候比"忘了"更糟。

## 你说对的地方

关键点在于**把"记忆"和"上下文"解耦**：

```
以前：存档 = 完整对话 → 载入时全塞回去 → 撑爆
你的方案：存档 = 对话 + 记忆书 → 载入时只带最近几轮，旧的按需检索
```

这和人类是同一个机制：你不会每天回忆全部人生，但朋友提一句"上次你说想学吉他"，你能想起来。**记忆在，但不是常驻。**

而且你项目里已经有 `story_rag.py` 这套检索基建（BM25 + 4592 条索引），做这件事不用从零搭。

## 需要定清楚的五件事

**1. 用什么判据触发**

别看"轮数"，看**估算 token**（中文字符数 × 1.5 左右近似）。因为花钱和上限都是按 token 算的，轮数不可靠——一轮可能十个字，也可能两千字。

**2. 记忆条目什么时候生成**

**存档的时候生成，不要载入的时候现算。**

存档时是离线、可控的：让模型把这段对话压成 5~10 条"记忆条目"存进 save 文件（比如"玩家说过不喜欢下雨""约定周末去海边"）。载入时直接读现成的，零成本。

如果放到载入时才算，每次进游戏都要跑一次总结，又慢又贵——还容易卡在进入界面那几秒。

**3. 检索用什么方式**

光靠 BM25 会漏。对话记忆很多是**语义相关但字面无关**的：

> 玩家问"今天适合出门吗" → 需要想起"他说过讨厌下雨"

字面上"出门"和"下雨"不重合，BM25 抓不到。

所以建议：**关键词检索 + 最近时间加权**（近期条目优先），先不做向量。真不够再上向量，别一上来就堆。

**4. 检索结果怎么注入**

不要塞进 system prompt 里当设定（会和世界书打架）。更好的做法是**包装成"回忆"再给模型**：

```
[回忆] 你想起来，前几天他说过讨厌下雨。
```

这样模型会自然地在对话里带出来，而不是像查数据库。

**5. 查不到的时候怎么办 —— 这条最重要**

最危险的不是"记不住"，是**记不住还硬编**。

必须给模型一个明确的兜底指令：

> 如果记忆里没有相关内容，就用模糊的方式带过（"记不太清了"），不要编造具体细节。

角色扮演里"她记不清了"是完全合理的，甚至比"她什么都知道"更像人。**编造才是毁灭性的**——玩家一旦发现她编，信任就没了。

## 我建议的实现顺序

1. 存档时生成 **5~10 条记忆条目**（存进 save 的 `memory` 字段）
2. 载入时：最近 N 轮原文 + 全部记忆条目（条目少，全带也不贵）
3. 等条目多到带不动了，再上检索

**第 2 步其实已经能解决大部分问题了**——因为压缩后的条目体积极小，几十条也就几百 token，根本不需要检索引擎。

先跑通"压缩"，再考虑"检索"。别一上来就做 RAG，那是给自己加难度。

## 一个副作用，可能是好事

这套做完之后，你的存档会变得**更有"记忆"的味道**：

- 原始对话是"日记"
- 记忆条目是"印象"

玩家读档回来的感觉，会更像"她记得你这个人"，而不是"她有一份聊天记录"。

---

顺带说：这个设计里最难的其实不是技术，是**决定记什么**。"玩家说了句好笑的吐槽"要不要记？"他今天心情不好"要不要记？这些判断标准，最后会变成这个角色的性格。

回头可以做个小测试：让模型自己挑 5 条它认为最重要的，看看它挑什么——那个答案会很有意思。

## 用户

那大概就是这样：我们设置一个token阈值，每次存档的时候自动测算当前记录有没有超过这个阈值超过了就自动以记忆书机制存档，在读档的时候就只把记录里最近的一段对话作为上下文发送给模型（这部分的长度也需要探讨），没有超过的话就直接发送给模型。但是这一整套机制都不显示在前端，避免影响体验。但是呢在回想界面里这些文本还是得按照原来的方式显示，并且可以选取。就是说前端看上去一切都不变，只改后端。

## 烬

方案我完全清楚了，而且这个设计是**对的**——因为它把"存档的内容"和"发送给模型的内容"分开了。

我先说说我认为最关键的一点，然后列出还需要定的参数。

## 你这个设计里最漂亮的地方

```
存档文件：永远完整（回想要能翻到每一条）
发送给模型的上下文：永远可控（不会撑爆）
```

**两者解耦**。而且因为回想读的是存档里的原始记录，所以**前端一行代码都不用改**——这一点非常干净，很多产品做不到。

## 还需要定的几个参数

### 1. 阈值定多少

建议：**模型上下文长度的 60%**。

留 40% 给：人设 + 世界书 + 记忆条目 + 本轮回复 + 安全余量。

### 2. "最近一段"取多长

这个不能按轮数，要按 **token**。

建议 **8000 token 左右**（可配）。约等于 20~40 轮日常对话，足够让模型知道"刚才在聊什么"。

而且要**从用户消息对齐**——不要从半句话开始截。

### 3. token 怎么算

不引入 tokenizer，用近似公式就够：

```
中文：1 字 ≈ 1 token
英文：4 字符 ≈ 1 token
```

误差 10~15%，但阈值留了 40% 余量，无所谓。**别为了精确去装 tiktoken**——那个依赖不值得。

## 两个必须注意的坑

### 坑 1：每次存档都重新总结 → 会漂移

如果每次存档都把**整段历史**重新总结一遍：

- 慢且贵（存档会卡住）
- **内容漂移**：同一段对话总结三次，可能得出三个版本，越总结越失真

**正确做法：增量。** 每次只总结"这次被截掉的那一段"，追加到记忆条目里，老条目不动。

像滚雪球，不是重新捏一个雪球。

### 坑 2：存档时同步生成摘要 → 卡

让模型总结要几百毫秒到几秒。如果存档时同步等它，玩家点了存档会感觉卡了一下。

**正确做法：**

1. 先把存档落盘（`messages` 完整写入，立即返回成功）
2. 摘要**异步补写**进同一个文件（`memory` 字段先写"生成中"）
3. 万一摘要失败，读档时**降级为全量发送**——不能因为摘要失败导致读不了档

## 一个体验上的隐患

**"她忽然想不起来了"。**

阈值触发那一刻，旧的对话就从上下文里消失了。如果玩家刚读档就问"我们上次说到哪了"，模型只能靠记忆条目回答，可能答得含糊。

两个缓解办法：

1. **记忆条目里专门留一条"当前剧情进展"**——用 2~3 句概括"刚发生到哪儿了"，优先注入
2. **别在对话中途切换**，只在**读档**时判断（你原方案就是这样，很好）。这样切换点总是在"重新进入"的时刻，玩家心理上更容易接受"她需要想一想"

## 还有一件事：检索什么时候上

你的方案是"载入时带最近段 + 记忆条目"。这个组合能撑很久。

真正需要检索，是**记忆条目多到带不动**的时候（比如超过 200 条 / 4K token）。到那时再加：

```
玩家每说一句 → 用这句去检索 top-5 相关条目 → 注入
```

**先别做。** 先把"摘要 + 全带条目"跑通，那已经能解决 90% 的问题了。

## 关于"不显示在前端"

这点我特别赞成，而且想强调一下：

很多产品会弹一句"为节省上下文，早期对话已折叠"——**这是工程语言，不是人话。**

折叠是工程语言，记忆是人话。

整套机制对玩家不可见，意味着：

- 存档界面显示的还是"共 87 条对话"
- 回想里能翻到每一条原文
- 玩家感知不到"她失忆了"，只会觉得"她记得我这个人"

---

这套东西实现起来大概分三块：存档时算 token、异步生成条目、读档时裁剪上下文。都不大，但每一块都要能"失败后降级"，不然会把存档搞坏。

下次开工可以从"存档时算 token 并落一个空 memory 字段"开始——**先把数据结构加进去，旧的存档照样能读**，风险最低。
